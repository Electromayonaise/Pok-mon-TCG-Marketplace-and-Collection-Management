# Implementability review — Plan-2 architecture

**Report 1 of 3** (task statement §3.0.2). The review asked one question of every one of the 37 core operations: *could an agent implement this from `ARCHITECTURE.md` alone without choosing something the document does not say?* It also asked it of each Solu-2 deliverable that the Plan-2 architecture never had to produce. Solu-1's four deferred findings (E-15, T-07, F-7, F-12) are re-examined here, as the statement requires.

The review is a self-review under the skill's adversarial brief. Mateo decides the triage at the Phase 0 gate. Owners follow the statement: **A** = Mateo (Architect-lead, Phases 0–2), **B** = Martín (Test-lead, Phase 3).

## Findings

### Deliverables the architecture never had to define

- **G-01 The event envelope has no `schemaVersion` and no named `occurredAt`.** §7.1 fixes the payloads ("this document adds no field", AD-9). `OutboxEvent` has only `id`, `type`, `aggregateId`, `payload` and `createdAt` (AD-SYS-2 rule 2). `events.md` must carry `eventId`, `occurredAt` and `schemaVersion`. An agent would have to choose whether these go into the payload, which AD-9 forbids, or into the envelope, and how a version is numbered and bumped.
- **G-02 No wire contract exists for the ingress procedures.** The module sections name every tRPC procedure, its builder and its codes. Nothing fixes the HTTP method, path, request encoding or response envelope. `openapi.yaml` cannot be written without inventing one, and two plausible inventions conflict: describing tRPC's own HTTP wire, or adding a REST adapter (`trpc-openapi`), which is a second router.
- **G-03 `ErrorBody` is undefined.** AD-SYS-1 defines the `Decision` and the family → tRPC-code table, and S-2 requires byte-identical bodies for "hidden" and "unknown". The architecture never says what the error formatter emits: where the registry code sits, whether the `Decision` travels whole, where zod issues go for `RequestValidationFailed`, and how `occurredAt`, the one field S-2 exempts, is encoded.
- **G-04 There is no `audit_events` table, and AD-8 makes adding one a decision.** The statement requires an `audit_events` table. Plan-2 instead has ten per-module append-only audit tables (AD-SYS-8 rule 10). AD-SYS-2 rule 10 lists the only tables `shared-kernel` may own. An agent would have to choose among three options: a new shared table, which breaks that list; a view over the ten tables; or a renaming of one of them.
- **G-05 There is no `createdAt` / `updatedAt` convention.** Only `BusinessProfile` and `SupportContactSetting` carry `updatedAt`. AD-SYS-6 rule 1 bans SQL `now()`, so a `DEFAULT now()` is not allowed. Append-only tables have `UPDATE` revoked, so an `updatedAt` there could never change. Their existing `at` and `openedAt` columns overlap with a `createdAt`. An agent would have to choose the columns, their source, and what to do on append-only tables.

### Operations whose behaviour the architecture leaves open

- **G-06 Annex A's operation names are not the architecture's names, and `cancelTrade` is ambiguous.** Eight operations are not ingress procedures at all:
  - `claimSellerTrack`, the shared step inside `access.completeIndividualProfile` and `verification.submit`;
  - `requireListingEligibility`, `requireMessagingEligibility` and `assertSearchArea`, which are guards;
  - `upsertCatalogEntry`, a feed-batch step;
  - `applyCommissionProjection`, `applyOrderDeduction` and `onOrderClosed`, which are subscribers.

  Others map to differently named procedures: `acceptPrompt` is `collections.prompts.accept`, and `traceCapabilities` is `access.traceCapabilities`. `cancelTrade` could be `trading.cancel` (Accepted → Cancelled, releases the reservation, AD-TRD-3) or `trading.withdraw` (Open → Withdrawn, no reservation, AD-TRD-1). Without one map, the contract's *Layer* field, the OpenAPI path list and the Solu-1 → Solu-2 stub reuse would each be guessed separately.
- **G-07 The ORD mandatory edge case "business confirms before paid" has two incompatible codes** (Solu-1 F-7, carried). *[CORRECTED at the Phase 1 gate, decision log #7: PRD FR-ORD-4 already names `OrderNotVisibleToCaller` for this case, so only ARCHITECTURE is silent and the claim of "two incompatible codes" was overstated. The resolution below is unchanged.]* AD-ORD-2 rule 3 maps only "item before paid" to `OrderConfirmationOutOfOrder`. AD-ORD-3 rule 1 hides an unpaid order from its business, so the same call reaches `OrderNotVisibleToCaller`. An agent who reads rule 3 by analogy would return 409 `OrderConfirmationOutOfOrder` to the business, and that confirms the order exists, which AD-15 and S-2 forbid.
- **G-08 A buyer cancel has no `cancelReason` value.** AD-ORD-2 rule 6 sets `'Unpaid'` on expiry and says cancel "is identical". Solu-1's schema already requires a reason on every terminated order (review E-07, `order_reason_iff_terminated`), so a cancel that writes `NULL` violates a CHECK. No document names the buyer-cancel value or the allowed set.
- **G-09 The optimistic `version = :v` of AD-TRD-1 has no source.** Every trade action's predicate includes `version=:v`, and the stale-tab guarantee rests on it. No procedure input in §6.8 carries a version. If an agent reads `:v` inside the transaction, the predicate is always true and the guarantee silently disappears. `counterOffer` and `acceptOffer`, two of TRD's three core operations, depend on it.
- **G-10 A top-up can be confirmed for a business whose commission account does not exist yet.** The account is opened only by the `BusinessApplicationApproved` subscriber (AD-COM-1 rule 5). `LedgerService.apply` throws `'Unexpected'` when the row is missing (rule 1). That is safe for a subscriber, which is retried by replay. For `confirmTopUp`, an admin command and a core operation, it means a 5xx on a legal input whenever that delivery is still `pending` or `failed`. Nothing says whether `requestTopUp` must refuse first, or which code it uses.
- **G-11 The latency clause "p95 < X ms at N concurrent" has no N, and about half of the 37 operations have no module budget.** The PRD §7 protocol takes 500 sequential samples. Concurrency appears only in the correctness NFRs (50 connections × 100). Operations such as `traceCapabilities`, `counterOffer`, `cancelTrade`, `acceptPrompt`, `hideReview` and `reconcile` have no module p95. An agent would invent a number unless the fallback (NFR-SYS-9: reads 1,000 ms, commands 800 ms) and the concurrency level are fixed once.
- **G-12 The error catalog's `retryable` column has no source.** The architecture defines only the transaction helper's internal retry (40P01/40001, twice, then `'Unexpected'`, AD-SYS-4 rule 6). Whether a client may retry `ContactRateLimited`, `FeedRunInProgress`, `TradeOfferNotOpen` or `'Unexpected'` with the same input is never stated.

### Stack and repository

- **G-13 There are two schema sources of truth.** §3 and §4 name `prisma/schema.prisma` as "one schema" and Prisma 7.6 as the stack. The statement asks for `001_tezg_schema.sql`, and Solu-1 already went SQL-first because Prisma cannot express what the invariants need: the `tezg_is_cuid` CHECKs, partial unique indexes, composite seller-track FKs and per-table grants. Left open, the package would carry both, and they would drift.
- **G-14 Solu-1 and Solu-2 share one code root, and Solu-2 can break Solu-1's gate.** Solu-1's stubs, DTOs and harness live at the repository root, and about half of the 37 operations overlap its 37 contracts. A Solu-2 rename or signature change would turn Solu-1's audit C3 (DTO binding) and its 131-test red check into failures. Nothing says whether Solu-2 extends or replaces.

### Solu-1 deferrals re-examined

- **G-15 E-15: deleting a collection still drops platform-purchase entries forever.** FR-COL-1 keeps it as an `[ASSUMPTION]` ("user-owned data"), and `CollectionEntry` cascades. Neither says what the confirmation tells the owner about `PlatformPurchase` entries, or what `acceptPrompt` does when its target collection is gone. Its error list allows only `CollectionNotFound`, and whether the prompt then stays `Pending` is unspecified.
- **G-16 T-07: "a complete explanation" has no checkable definition.** `citations: [{ rule, inputs }]` fixes the shape but not the format of `rule`. The statement's `explain_assert` fixture needs one. Solu-1's contracts cite `rule` values in three styles (`AD-…`, `FR-…`, `AD-… rule n`).
- **G-17 F-12: no inventory maps UI states to contracts.** §9.1 says every rendered state carries `decision: Decision`. No table lists, per page spec, which states exist and which contract and DTO field back each one. Readiness check 2 ("every UI state backed by a contract and a DTO") cannot be automated without that table.

## Triage

Mateo accepted all 17 resolutions as recommended at the Phase 0 gate on 2026-10-18 (decision log Solu-2 #6). For G-04 he chose the shared-kernel table with a port over a view and over replacing the module tables. For G-05 he chose `updatedAt` on mutable tables only over both columns everywhere.
