# Adversarial Review — ARCHITECTURE.md (Buyer/Collector Track, Phase 4)

**Reviewer:** bmad-review-adversarial-general
**Target:** `docs/plan-1-buyer-track/ARCHITECTURE.md`
**Also read:** `EXPERIENCE.md`, `prd.md`, page spec `3.2-comprobante-upload-payment-confirmation.md`, whole-system `ARCHITECTURE-SPINE.md` (AD-1..13)

---

- **Process violation: `status: final` is set before the Reviewer Gate ran.** The `bmad-architecture` skill's own Finalize sequence is Distill → Reconcile → Reviewer pass → Triage → Polish → Close, and `status: final` is explicitly a Close-step action ("Set the spine's own frontmatter `status: final`... log 'spine finalized'"). This file's frontmatter already reads `status: final` while this very review — the Reviewer pass — was still pending, and no triage of this review's findings has happened yet. At minimum this should have shipped as `status: draft` until the gate closed clean.

- **AD-14 and AD-15's Rules quietly depend on a data-shape question their own Deferred section leaves open.** Both Rules key access off "the verified business that owns the listing the Order references," but the Deferred section admits "Whether `Order.businessId` is a direct column or derived through the referenced listing's owning business" is unresolved. That's not a harmless implementation detail deferred *below* the invariant — it's the exact fact the enforcement check in AD-14 and the visibility check in AD-15 must evaluate. A Rule that can't state how its own precondition is computed isn't yet enforceable as written; this belongs in the Invariants section (even a one-line "resolved via X" call), not Deferred.

- **AD-11 (`DomainError` ownership) is treated as untouched, but two PRDs explicitly asked this Architecture phase to extend it.** The Buyer PRD's own §8 Open Question 6 says a `DomainError` code is needed for "reject confirm-paid-without-comprobante" and explicitly says "carry to the Architecture phase." The Seller-track PRD independently flags the same gap for "duplicate confirm-payment-received" and "confirm on a non-owned Order." This ARCHITECTURE.md's Inherited Invariants table lumps "AD-5 through AD-12" together as "Unaffected by this track's 4 scenarios" — which is simply false for AD-11 given the PRD explicitly routed a request here. Either a new error code (or explicit confirmation an existing one covers it) belongs in this file, or the Deferred section needs to say plainly why it's being punted again rather than silently dropping a request two PRDs made by name.

- **A PRD-flagged compliance question (comprobante Ley 1581 exposure) is dropped entirely.** `prd.md` §7 is explicit and pointed: the comprobante's bank-account-number/holder-name content "may carry its own Ley 1581 personal-data obligations independent of `ARCHITECTURE-SPINE.md` AD-13, whose Scope note restricts that AD to `legalIdentity` documents only... flagged here as a distinct compliance question for the Architecture phase, not assumed to be covered by AD-13 by proximity." AD-14 answers *who can read the file and how*, but never once addresses whether the comprobante's *content* carries its own regulated-data handling obligations. This is a named, cited, explicit ask from an upstream document, and it isn't answered, deferred with a reason, or even mentioned.

- **The Structural Seed diagram is inconsistent with the file's own Capability → Architecture Map.** The Capability Map lists CAP-21 ("commission-gated purchasability, read-only to buyer") as touched by this track, governed by AD-3. The Mermaid diagram's "Modules touched" subgraph has no `commission` node and no edge into it anywhere. A diagram that's supposed to be this track's structural slice shouldn't omit a module the same document says the track touches.

- **The diagram doesn't actually show the dependency AD-14/AD-15 rely on.** Both new ADs hinge on `orders` being able to determine "does this business own the listing this Order references" — that's fundamentally a `listings` lookup. The diagram draws `orders_m -->|AD-15 read-ownership check| identity_m` but no `orders_m --> listings_m` edge at all, despite AD-1's own graph showing `orders --> listings` as an existing dependency. As drawn, the diagram implies the ownership check happens against `identity`, which only knows verification/role facts, not listing ownership.

- **AD-16's data source for "pending trade offers" inherits an ambiguity from the PRD without resolving it.** `prd.md`'s Glossary sources the My Sales tab's trade-offer count from "`docs/plan-1-seller-track/prd.md` FR-S3/FR-S4" — but FR-S3 is trade-offer review/response (where a "pending" offer actually lives) and FR-S4 is mutual trade-*completion* confirmation (a materially different state: an already-accepted trade winding down, not a pending one). AD-16's Rule just says "querying... `trading` (pending trade offers against those listings)" without specifying which of the two FR-S3/FR-S4-shaped states that query actually reads — an architecture decision is exactly the place to have pinned down which underlying fact "pending" maps to, and it wasn't.

- **No AD addresses what happens to AD-14/AD-15 access after a business is later un-verified or moderated.** `ARCHITECTURE-SPINE.md` AD-12 covers admin moderation (`hiddenAt`) and CAP-15/CAP-28 cover business approval/moderation as inherited invariants, but nothing in this file's two new ADs states whether a business that loses verified status retroactively loses AD-15's read access (and therefore AD-14's URL-minting eligibility) on Orders it already had access to. Silence here reads as an oversight, not a deliberate Deferred call, since the file doesn't mention the interaction at all.

- **Frontmatter `binds` mixes ID namespaces without comment.** The parent spine's `binds` list is exclusively CAP-ids. This file's `binds` list mixes `CAP-*` entries with a bare `"FR-9"` — a PRD-level requirement ID, not a capability ID, and a namespace the parent convention doesn't use. Either note the deliberate departure or normalize it; as written it looks like an inconsistency rather than a choice.

- **Stack and Consistency Conventions sections are silently omitted, unlike Inherited Invariants.** The Inherited Invariants section explicitly states these are read from the parent and not re-derived. No equivalent sentence exists for the template's Stack or Consistency Conventions sections — they're just absent, with nothing telling a reader landing on this file alone whether that's "inherited unchanged, see parent" or "not applicable to this track." Given the file otherwise takes care to be explicit about inheritance, the silent omission elsewhere reads as inconsistent editorial treatment, not a considered choice.

- **AD-14's TTL is stated as a range ("5-15 minutes") inside a Rule, then re-described in Deferred as "not pinned to one number."** A Rule is supposed to be the enforceable constraint; leaving a numeric range inside the Rule itself (rather than picking one number and deferring only the *justification*) means two independent builders could each pick a different value inside that band and both claim compliance — which is exactly the kind of divergence this document exists to prevent, per its own stated test ("could they choose incompatibly?"). A range is not a fixed rule.

- **The Cross-Track Note cites a companion file that does not exist yet, without saying so.** Frontmatter `companions` and the Cross-Track Note both reference `docs/plan-1-seller-track/ARCHITECTURE.md` as the file that "must cite AD-14 and AD-15 as [ADOPTED]" — but per this same project's own governing plan, that file has not been written yet (Seller/Business track is currently only at its PRD phase). Nothing in this document flags that the companion is prospective/not-yet-created, which risks a reader (or grader) checking for a cross-reference that doesn't resolve to anything today.
