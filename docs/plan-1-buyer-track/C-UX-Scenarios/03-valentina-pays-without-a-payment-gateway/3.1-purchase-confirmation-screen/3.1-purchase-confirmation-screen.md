## Overview

**Page Purpose:** Confirm the purchase of a verified-business listing and receive an `OrderId` plus the business's payment details (QR/bank account) (FR-4, CAP-17).

**User Situation:** Decision already made — on the verified-business listing she picked in Scenario 02, ready to buy. Hopes to pay quickly via her own banking app and have proof she did her part; worried about sending money with no receipt.

**Success Criteria:** Order created (`OrderId` issued, listing quantity decremented), payment details displayed clearly enough to act on immediately.

**Entry Points:**
- ← 2.1 Listing Search Results & Comparison (tapping "Buy Now" on a business listing, same session).

**Exit Points:**
- Leaves TEZG to pay via her own banking app, then → 3.2 Comprobante Upload (primary path).
- → 4.1 Orders List, via "Finish payment later" (abandoned-purchase path, Phase 3A Key Decision).

## Page Sections

### Order Header

**OBJECT ID:** `purchase-confirm-orderid-header`

| Property | Value |
|----------|-------|
| Content | "Order #{OrderId}" |
| Behavior | `OrderId` is issued and the listing quantity decremented the moment this page is reached (FR-4's testable Consequence) — not on a later confirmation |

### Payment Details Block

**OBJECT ID:** `purchase-confirm-payment-details-block`

| Property | Value |
|----------|-------|
| Component | [`{components.payment-details-block}`](../../../DESIGN.md) |
| Content | QR code image, bank name, account number, payment reference (the `OrderId` or a short code derived from it) |
| Accessibility (resolves a Phase 3A Reviewer Gate finding) | The QR code is a convenience, never the only way to get the information: bank name, account number, and reference are always rendered as plain, selectable/copyable text alongside it — never QR-only. QR image carries `alt="QR code encoding the same bank account and reference details shown as text below"`. This is the highest-stakes content block on the track — misreading it risks sending real money to the wrong place, so the text values use `typography.price-figure`-grade tabular-nums for the account number to prevent digit transposition errors. |

### Instructions

**OBJECT ID:** `purchase-confirm-instructions-text`

| Property | Value |
|----------|-------|
| Content | "Pay using your banking app, then come back to confirm." |

### Upload Proof CTA

**OBJECT ID:** `purchase-confirm-upload-proof-button`

| Property | Value |
|----------|-------|
| Component | `{components.button-primary}` |
| Content | "I've Paid — Upload Proof" |
| Behavior | Navigates to 3.2 |

### Finish Later Link

**OBJECT ID:** `purchase-confirm-finish-later-link`

| Property | Value |
|----------|-------|
| Content | "Finish payment later" |
| Behavior | Navigates to 4.1 Orders List, where this Order appears as "Awaiting payment" with its own "Finish payment" action back to this flow (Phase 3A Key Decision — abandoned purchases are never lost) |

## Page States

| State | When | Appearance | Actions |
|-------|------|------------|---------|
| Default | Order just created | Full payment-details-block, both CTAs available | Upload proof now, or finish later |
| Loading | Order creation in flight (brief) | Skeleton in place of the payment-details-block | None |
| Error — order creation failed | Server rejects (e.g., listing sold out in a race) | Inline error: "This listing is no longer available — someone else may have just bought it" with a link back to 2.1 | Return to listing comparison |

## Technical Notes

- This page has zero shared component coverage before this spec — `{components.payment-details-block}` was defined in DESIGN.md during Phase 3A specifically to close that gap; this page is its sole consumer.
- No payment gateway integration exists or is planned (SPEC.md constraint) — this page's entire design premise is presenting static payment details for an external, out-of-band transfer.
