# Adversarial Review: DESIGN.md + EXPERIENCE.md (Plan-1 Buyer/Collector Track)

Reviewed against: `prd.md` (FR-1..FR-9), `C-UX-Scenarios/00-ux-scenarios.md`, the 4 scenario outlines, the 10 page specs, and `_bmad-output/specs/spec-pokemon-tcg-marketplace/SPEC.md` (CAP-3, CAP-20, CAP-22, CAP-27, and the no-native-device-feature-dependency constraint).

Both documents carry `status: final`. That status is not earned by the gaps below.

- **CAP-3's currency requirement is silently dropped.** SPEC.md's CAP-3 success criterion is explicit: "listing price in COP, last-transaction price as a single USD/COP reference point." Neither DESIGN.md nor EXPERIENCE.md mentions currency anywhere — no COP formatting, no indication of how a COP listing price and a USD/COP reference price are reconciled for visual comparison. The entire trust narrative of this track (Typography section: "tabular-nums keeps their digits aligned so a user can visually compare them at a glance") falls apart if the two numbers being compared are denominated in different currencies without any stated conversion or dual-display treatment. This is not a cosmetic omission; it is the mechanism the whole price-trust pitch depends on, and it is unaddressed.

- **The core seller-type comparison mechanic on page 2.1 is never actually specified.** The page spec for 2.1 calls the individual-vs-business distinction "the page's core comparison." Scenario 02's climax is that the verified-business listing is "purchasable directly" while an individual-seller listing "would only generate a contact message." Yet `{components.listing-card}` in EXPERIENCE.md only says the card is "tappable as a whole... to reach Card Detail View or, from search results, directly toward purchase," and DESIGN.md's listing-card component defines only a text seller-type label — no differing CTA (e.g., "Buy" vs. "Contact Seller"), no differing tap behavior. The single interaction that realizes FR-4/CAP-17's purchasability distinction is left undefined by both documents.

- **The individual-seller "contact message" branch has no surface, no state, and is quietly excluded from the "closure check."** EXPERIENCE.md's IA section claims: "every stated need in the 4 scenario outlines has exactly one surface... no orphaned pages." But page spec 2.1 explicitly describes tapping an individual-seller listing as leading to a generated contact message (CAP-6) — a real interaction outcome on an in-scope page — and no page, modal, or state anywhere in the IA table, Key Flows, or Component Patterns accounts for what that produces. The "closure check" is only true because the contact-message outcome was never counted as a "stated need" in the first place, despite the page spec itself flagging it as core page content.

- **FR-4's `NotBusinessListing` rejection has zero copy, zero visual state, zero placement.** This is a testable PRD Consequence (FR-4) and page spec 2.1 explicitly flags it as "an edge case noted here for Phase 4's page spec" — i.e., this document was the one supposed to resolve it. Voice and Tone carefully specifies copy conventions for comprobante failures but never mentions this rejection at all. There is no error-state definition for it anywhere in either document.

- **Page 3.1 (Purchase Confirmation Screen) has no dedicated component coverage at all.** This page's entire job, per FR-4/CAP-17 and the page spec, is displaying an `OrderId` and the business's payment details (QR code, bank account). DESIGN.md's Components section defines listing-card, price-block, order-status-row, upload-dropzone, button-primary, and empty-state — none of which apply to a QR code / bank-details / OrderId block. A QR code is a high-contrast, blocky graphic that the "flat ledger page, no drop shadows, no gradients" visual language never actually addresses. One of the ten specified surfaces is designed by omission.

- **No accessibility treatment for the QR/bank-details content on 3.1.** The Accessibility Floor section itemizes behavioral requirements for price-block, order-status dots, and the upload dropzone, but says nothing about the QR code image or bank-account text — arguably the single highest-stakes content block in the entire track, since misreading it means sending real money to the wrong place. No alt-text requirement, no text-equivalent-of-QR requirement, nothing.

- **Comprobante upload never discloses the 5 MB size cap before failure.** FR-5's NFR fixes a hard 5 MB ceiling, and the Idle-state copy is specified verbatim: "Upload a photo of your transfer confirmation" — no size guidance. The 5 MB limit only surfaces reactively, as one of three possible causes bundled into the generic Failure-state copy ("bad format, upload timeout, file too large"). A user has no way to avoid the failure in advance, which directly undercuts SM-2 (upload-to-confirmation speed) and SM-C1 (don't let upload-speed pressure degrade comprobante legibility) by inviting exactly the wasted-attempt friction those metrics are trying to avoid.

- **No path to replace a comprobante after it reaches the Success state.** The five states (Idle → OS picker → Uploading → Success → Failure) provide no way back to Idle from Success. If Valentina uploads the wrong screenshot — a real, likely error given this is a photo of her own banking app — before tapping "Confirm I Paid," there is no specified "change photo" affordance. The document calls these "five explicit states, all required" as if the state machine were complete, but a legitimate, common user correction path is missing.

- **The OS-picker-cancelled case is undocumented.** State 2 ("OS picker open") is described as needing "no TEZG-side state... beyond triggering `<input type=\"file\">`." What happens when the user opens the OS chooser and backs out without selecting anything is never stated. Given the document's own insistence that all states are "explicit" and "required," silently assuming the cancel path collapses back to Idle is an assumption, not a specification.

- **DESIGN.md's Empty State component description contradicts EXPERIENCE.md's own State Patterns section.** DESIGN.md says the Empty State component is "used for zero-active-listings catalog entries and the My Sales tab with no listings." But EXPERIENCE.md's "Zero-active-listings catalog state" section is explicit that a zero-listing card "still appears in browse/filter results" (1.2) — it is not an empty state there at all, merely a tagged row — and the actual empty-state copy ("No active listings for this card right now") only appears on the Card Detail View (1.3), replacing the listing list. DESIGN.md's own component catalog misattributes where its own pattern applies.

- **The IA section misdescribes its own navigation hub.** EXPERIENCE.md states: "Account menu is the hub connecting scenario 01 (fresh session) to scenario 04 (return visit)." But per the same document's IA table, Scenario 01 begins unauthenticated at "App entry" and never touches the account menu — 1.1 Sign Up isn't reached from it, and nothing in Scenario 01 is reached from it. Only Scenario 04 (4.1 Orders List) is reached from the account menu. The claim that the account menu "connects" scenario 01 to scenario 04 is simply inaccurate on the document's own terms.

- **Trend-direction color-coding has no confirmed non-color fallback.** The Accessibility Floor guarantees that the three price-block values (listing/reference/trend) are distinguished from each other by label, not color alone — but it never states that trend direction itself (up vs. down within the trend value) is distinguished by anything other than `trend-positive`/`trend-negative` color. A signed percentage figure would resolve this trivially, but the documents never commit to showing a `+`/`-` sign or directional glyph alongside the color, leaving an accessibility gap the floor's own stated rigor elsewhere does not tolerate.

- **Scenario/page-spec metadata that DESIGN.md and EXPERIENCE.md are supposed to be consistent with directly contradicts the "no camera dependency" story, unreconciled.** Scenario 03's outline lists Device as "Mobile (browser + camera for the comprobante photo)," and page spec 3.2's Platform field literally reads "Mobile (browser + camera)" — language that reads as a first-class camera hardware requirement. EXPERIENCE.md's Foundation section resolves this correctly in substance (OS file-picker, not custom camera integration), but it never acknowledges or corrects the upstream documents' own "+ camera" platform labeling, leaving two "final"-status documents in this same folder set describing the same page's platform requirement in materially different, superficially contradictory terms.

- **Sign Up (1.1) — one of the ten "designed" surfaces — has no validation, error, or tone treatment whatsoever.** FR-1 requires "no additional onboarding step blocking access," which DESIGN.md/EXPERIENCE.md interpret only as "don't add extra steps," but a signup form still needs to handle duplicate email, weak password, or network failure. Voice and Tone defines copy conventions in detail for payment and comprobante errors but is completely silent on account-creation errors, despite 1.1 being formally in scope and formally "final."
