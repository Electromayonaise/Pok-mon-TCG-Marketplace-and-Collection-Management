# Peer Review Remediation & Traceability

Maps every finding from the Workshop 2 peer review (`docs/Martin's specification peer review.pdf`) of Spec 1 (`docs/spec-task-1/SPEC.md`) to its root cause and its concrete remediation in Spec 2 (`_bmad-output/specs/spec-pokemon-tcg-marketplace/SPEC.md` + `ARCHITECTURE-SPINE.md`). The peer review scored Spec 1 across 8 dimensions:

| Dimension | Spec 1 verdict |
| --- | --- |
| Clarity | Medium |
| Scope Control | Strong |
| Verifiability | Strong |
| Atomicity | Weak |
| Consistency | Medium |
| Implementation Independence | Medium |
| Traceability | Strong (as a package with its Contract+JUSTIFICATION companions), Weak (spec alone — no stable IDs) |
| Decomposition Readiness | Medium |

## 8-Dimension Traceability Matrix

| Dimension | Issue / Finding from Workshop 2 | Root Cause in Spec 1 | Action Taken & Specific Section/ID in Spec 2 |
| --- | --- | --- | --- |
| **Clarity** | Unverifiable, non-falsifying prose survived into constraint- and capability-level statements — e.g. a first-time seller's profile step was called "short" with no way to test that claim, and a UGC constraint said boundaries must exist without naming any. | Constraints and capability intents were drafted with qualitative adjectives instead of falsifiable rules. | `SPEC.md` CAP-19 dropped "short" (intent now: "completes a profile step before creating their first listing"). The UGC-boundary Constraint was replaced with a concrete rule: catalog/pricing data is platform-derived and never user-editable; only listings, reviews, and collection notes are user-generated content (Constraints, new bullet). |
| **Scope Control** | Already strong — Spec 1 carried 9 explicit Non-Goals, deliberately excluding schema, UI, deployment, and the pricing algorithm. | N/A — preserved, not a defect. | Spec 2 extends the same discipline: 19 Non-Goals (`SPEC.md` Non-goals), including two new exclusions tied to remediation itself — the exact moderation policy criteria (CAP-28 fixes the mechanism, not the rulebook) and (already-present) the price-estimation algorithm, now paired with the newly-sourced external-feed assumption. |
| **Verifiability** | Already strong on functional success signals, but silent on any non-functional/performance claim — nothing to verify against if a catalog query became slow. | Spec 1 never stated a performance expectation of any kind. | Added a Constraint with an informal but concrete NFR: catalog browse/filter queries target ~1-2s for a catalog on the order of a few thousand to tens of thousands of entries — course-project scale, explicitly not a load-tested SLA (`SPEC.md` Constraints). |
| **Atomicity** | Weakest dimension — several capability bullets bundled multiple independent behaviors into one sentence (e.g. one bullet covering bundle creation, listing, and contact/messaging together; another covering collection creation, binder view, and source-tagging together). | Capabilities were drafted at "feature paragraph" grain instead of one-behavior-per-capability. | Decomposed into 28 atomic capabilities with stable IDs (`SPEC.md` CAP-1..CAP-28), e.g. the original bundled bullet became separate CAP-6 (contact-message generation), CAP-17 (business purchase), CAP-18 (in-app messaging), CAP-19 (profile-step gate); the collection bullet became CAP-8/9/10/11/12/13. |
| **Consistency** | Two contradictions flagged: (i) capability text mentioned sealed products as sellable, but the Contract's `itemRef` type (`card \| BundleId`) had no case for them; (ii) `SellerNotVerified` and the individual-seller no-verification rule sat close enough in meaning to be misread as applying to the same account type. | The Contract's exact-signature layer and the capability-prose layer were authored without a cross-check pass between them. | (i) `SPEC.md` Constraints now states sealed products are always individually listed and never bundle components; `ARCHITECTURE-SPINE.md` AD-6 generalizes `InventoryUnit`'s key to `(sellerId, itemRef)` covering both cases explicitly. (ii) `ARCHITECTURE-SPINE.md` AD-11 now states explicitly that `SellerNotVerified` fires only for an unapproved-business listing attempt, never for an individual seller (whose only gate is the separately-owned `IndividualSellerProfileIncomplete`). |
| **Implementation Independence** | Spec 1's single Contract file mixed WHAT (behavior) with HOW (exact operation signatures, named error-code enums, return-type shapes) in one artifact, so a reader couldn't easily tell which parts were binding behavior vs. incidental interface choices. | No structural separation existed between behavioral intent and interface/implementation detail. | Spec 2's kernel Capabilities (`SPEC.md`) state intent+success only — no signatures, no enum literals, no return shapes. Those now live exclusively at the correct altitude in `ARCHITECTURE-SPINE.md` (AD-11's error ownership list, the Consistency Conventions table's money/ID/error-format rules) — a structural fix, not a rewording of the old Contract. |
| **Traceability** | Individual claims inside `SPEC.md`'s prose had no stable identifier — a reviewer or downstream builder had to quote a sentence to reference a specific requirement, and IDs only existed at the package level (via the Contract/JUSTIFICATION cross-references). | Spec 1's SPEC.md predates a capability-ID convention. | Every Spec 2 capability carries a stable `CAP-N` id (`SPEC.md` CAP-1..CAP-28, CAP-23 intentionally unused — see its memlog note), cited directly by `ARCHITECTURE-SPINE.md`'s `AD` `Binds` fields, its Capability→Architecture Map, and this remediation matrix. |
| **Decomposition Readiness** | Stakeholder-level admin-moderation responsibility (`stakeholders.md`: "moderate listings and user-generated information") was never turned into an actual capability or contract operation — an epic/story breakdown would have had to invent it or silently drop it. | A stakeholder goal was captured in the stakeholder matrix but never round-tripped into a Capability. | New `CAP-28` (`SPEC.md` Capabilities: admin hides/removes a policy-violating listing or review, record retained for audit) plus `AD-12` (`ARCHITECTURE-SPINE.md`: owning-module hide/unhide command, no shared moderation table) give moderation a concrete intent, success signal, and architectural home — ready to decompose into epics/stories without inventing scope at that stage. |

## Domain Realism Remediation (unflagged risky assumptions)

The peer review also flagged several domain-realism gaps that never surfaced as an explicit assumption in Spec 1 — these feed the assignment's separate Domain Realism criterion, not the traceability matrix above.

| Finding | Root Cause in Spec 1 | Action Taken in Spec 2 |
| --- | --- | --- |
| Catalog data source never named | Spec 1 assumed catalog data would simply exist, with no sourcing statement. | Already flagged as a Risky assumption in the session-2 kernel; carried forward unchanged (`SPEC.md` Assumptions). |
| Pokémon IP/licensing legality of displaying third-party card names/artwork never addressed | No legal-review statement of any kind. | Added Risky assumption: displaying Pokémon TCG names/artwork sourced from a third-party API is assumed permissible for this course-project's use case, not verified as licensable for a commercial launch (`SPEC.md` Assumptions). |
| Colombian data-protection law (Ley 1581, habeas data) never addressed for `legalIdentity` collection | Business-application data handling was specified functionally with no legal-compliance framing. | Added Constraint: `legalIdentity` data is regulated personal data under Ley 1581; the platform must apply lawful-basis/consent and secure-handling practices to it, mechanism deferred to architecture (`SPEC.md` Constraints). |
| Zero performance/scale expectations stated | See Verifiability row above. | See Verifiability row above (same fix serves both dimensions). |
| "Last transaction price" observability is doubtful given most sales are off-platform | Spec 1 implied the platform itself would supply this data with no sourcing statement. | Added Risky assumption: last-transaction price and historical trend are assumed sourced from an external price-aggregation feed, not derived from platform transaction history; existence of a usable, licensable source is unverified (`SPEC.md` Assumptions). Mirrored in `ARCHITECTURE-SPINE.md`'s CAP-3 architecture mapping and AD-6/pricing notes. |

## Process note

All remediation decisions above were confirmed with the user before being applied (directory-structure approach, the CAP-28-vs-Non-Goal choice for moderation, and the sealed-product inventory model were explicitly surfaced via clarifying questions rather than decided silently) and are logged, with rationale, in `_bmad-output/specs/spec-pokemon-tcg-marketplace/.memlog.md` and `_bmad-output/planning-artifacts/architecture/architecture-Pok-mon-TCG-Marketplace-and-Collection-Management-2026-08-25/.memlog.md`.
