## Overview

**Page Purpose:** Answer the three questions a shop owner has about money: how much is left, can people buy from me right now, and what do I need to do to change that. Also let the owner send a top-up request that an admin will check (FR-COM-2), and follow each request to its outcome.

**Success Criteria:**
- The balance, the purchasability state and, when paused, the exact minimum top-up are visible without scrolling on a 360 × 640 screen.
- A top-up request can be sent in one form, and its status is always visible afterwards.
- The page never shows a relative deadline or a countdown.

**Entry Points:**
- 5.2 "Recargar saldo" after approval;
- the 4.2 banner or the balance card in its header;
- the 7.2 header;
- the business desk rail (Saldo).

**Exit Points:**
- 7.2 ("Ver movimientos");
- 4.2 ("Ver mis publicaciones");
- 6.3 (desk rail).

## Page Sections

### Section: Balance Card

**OBJECT ID:** `com-balance-card`

| Property | Value |
|----------|-------|
| Component | `commission-balance-card` (inherited from Plan-1 seller track) |
| Figure | `balanceCop` in COP |
| State → indicator → copy | **Never funded** (account at $0, no confirmed top-up): `pending` dot, "Pausadas", "Recarga tu saldo para empezar a vender." **Low** (0 < balance < 20.000, FR-COM-9): `pending` dot, "Activas", the Low-balance copy with `{saldo}`. **Active** (≥ 20.000): `confirmed` dot, "Activas", no copy. **Exhausted** (≤ 0 after sales): `pending` dot, "Pausadas", the Exhausted copy with `{faltante}` = 1 − balance |
| Rate line | "Tarifa vigente: {tasa}" as a percent with up to two decimals ("8 %", "8,5 %"). If a future rate is scheduled: "Desde el {fecha}: {tasa}" |
| Links | "Ver movimientos" → 7.2; when paused, "Ver mis publicaciones" → 4.2 |

The low-balance notice is display only. It publishes nothing and changes no listing (FR-COM-9).

### Section: Top-Up Form

**OBJECT ID:** `com-topup-form`

| Property | Value |
|----------|-------|
| Amount | Integer COP input with a "$" prefix; thousands are formatted on blur. Out of range → `field-error` with the `TopUpAmountInvalid` copy, checked on submit and by the server |
| Reference | Text, 4–40 characters. Counter "{n}/40". Under 4 → "Escribe al menos 4 caracteres de la referencia de tu transferencia." |
| Comprobante | `upload-dropzone` with the FR-ORD-2 file rules and the same messages as 6.2 (types, size, "El archivo pesa {x} MB…") |
| Submit | `button-primary` "Enviar recarga". While sending: "Enviando…" |
| After success | The form clears; the new row appears at the top of the history as "En revisión"; the live region says "Recarga enviada. Estamos revisando tu transferencia." Focus moves to the new row |

### Section: Request History

**OBJECT ID:** `com-topup-history`

| Property | Value |
|----------|-------|
| Order | Newest first; 20 per page with "Ver más" |
| Row | `state-indicator` + amount + reference + submitted time; on decision, the decided time |
| Pending | `pending` dot "En revisión", with the Top-up pending copy on the newest pending row only |
| Confirmed | `confirmed` dot "Confirmada · {fecha}". The newest confirmed row shows the Top-up confirmed copy that matches the result ("resumed" or "still ≤0") |
| Rejected | `error` dot "Rechazada · {fecha}", then the Top-up rejected copy with the admin's reason, and "Nueva recarga" (scrolls to the form and pre-fills the amount) |
| Detail | Tapping a row opens `/tienda/saldo/recargas/<topUpId>` with the comprobante thumbnail. A request that is not the caller's → Not-available page (`TopUpNotVisibleToCaller`) |

## Page States

| State | When | Appearance | Actions |
|-------|------|------------|---------|
| Loading | First fetch | `skeleton` card + form + three history rows | — |
| Never funded | Just approved (COM-S1) | Card "$0 · Pausadas" + never-funded copy; history empty state "Aún no has enviado recargas." | Enviar recarga |
| Empty (history) | No top-up request has been sent | Covered by "Never funded": the history list shows "Aún no has enviado recargas." | Enviar recarga |
| Pending | A request is in review | History row "En revisión"; the card figure is unchanged | — |
| Active | Balance ≥ 20.000 | Card with `confirmed` dot | — |
| Low | 0 < balance < 20.000 (COM-S3, $12.000) | Card with the low-balance copy | Recargar saldo (scrolls to the form) |
| Exhausted | Balance ≤ 0 (COM-S3, −$2.400) | Card with "Recarga al menos $2.401 para reactivarlas." | Recargar saldo |
| Confirmed, resumed | A confirmation crossed zero (COM-S4) | On the next load or focus, the card shows $47.600 · Activas; the history row shows the resumed copy; the live region announces it once | Ver mis publicaciones |
| Confirmed, still short | A confirmation left the balance ≤ 0 | Still-short copy with the new `{faltante}` | Recargar saldo |
| Rejected | Admin rejected the request | Rejected copy with the reason | Nueva recarga |
| Error — validation | Amount, reference or file | `field-error` at the field; the form keeps its values | — |
| Error — transport | Submit not confirmed | §10 "No sabemos si…" copy with "Ver mis recargas" (refreshes the history). No automatic retry | Ver mis recargas |

## Technical Notes

- The page does not poll. It refetches on focus, because the only change it waits for (an admin decision) takes hours, and the median target is ≤ 24 h (PRD §22).
- `{faltante}` is computed by the server as `1 − balanceCop` and shown as-is; the client never does money arithmetic (NFR-COM-4).
- The card state comes from the account state (`Exhausted` / `Replenished`) plus the low-balance threshold. It is never derived from the listings' state.
- A resubmitted form after a transport failure can create a second pending request. The admin sees both in 7.3 with the same reference, and one can be rejected with the reason "Solicitud duplicada".
