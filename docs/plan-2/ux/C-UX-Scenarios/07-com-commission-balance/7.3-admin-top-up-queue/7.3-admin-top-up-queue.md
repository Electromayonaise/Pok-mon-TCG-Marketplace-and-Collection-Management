## Overview

**Page Purpose:** Let an admin check each pending top-up against the platform's bank statement and decide it once (FR-COM-3). A confirmation credits the balance in the same transaction, and when it crosses zero the business's listings resume. The page shows exactly what the decision did.

**Success Criteria:**
- The oldest pending request is first, and its waiting time is visible as an absolute submitted time.
- Everything needed to decide (amount, reference, comprobante, the business's current balance) is on one screen.
- Two admins can never both decide the same request, and the one who loses sees who won.

**Entry Points:** Admin rail → Recargas (the badge shows the pending count); a direct link to one request.

**Exit Points:** 7.2 admin variant ("Ver movimientos de {tienda}"); 1.3 account detail ("Ver cuenta").

## Page Sections

### Section: Queue List

**OBJECT ID:** `com-queue-list`

| Property | Value |
|----------|-------|
| Tabs | Pendientes (default) · Confirmadas · Rechazadas |
| Order | Pendientes: oldest first. The others: newest decision first |
| Row | `state-indicator` + shop name + amount + submitted time. A second pending request from the same business with the same reference shows the note "Misma referencia que otra solicitud pendiente" |
| Selection | The selected row is highlighted; the URL becomes `/admin/recargas/<topUpId>` |

### Section: Request Detail

**OBJECT ID:** `com-queue-detail`

| Property | Value |
|----------|-------|
| Facts | Shop (link to 1.3), amount, reference, submitted time, requested by (the owner's name) |
| Balance | The business's current balance and state, read-only |
| Preview | The server computes and shows the result before the decision: "Al confirmar, el saldo será {saldo} y sus publicaciones se reactivarán." / "Al confirmar, el saldo será {saldo}; sus publicaciones seguirán pausadas." / "Al confirmar, el saldo será {saldo}." (already active) |
| Comprobante | `document-viewer`, with zoom. It renders only the sanitized rendition (ARCHITECTURE AD-SYS-8 rule 11; the PDF rendition is pending G-5); there is no "Abrir en otra pestaña". The file is served from a short-lived link. On expiry, "Volver a abrir" fetches a new one (as in 6.3) |

### Section: Decision

**OBJECT ID:** `com-queue-decision`

| Property | Value |
|----------|-------|
| Confirm | `button-primary` "Confirmar recarga" opens a `<dialog>` because the credit cannot be undone: title "¿Confirmar la recarga de {monto} para {tienda}?", body "Confirme solo si la transferencia con la referencia {referencia} aparece en el extracto de TEZG.", actions "Confirmar recarga" / "Cancelar" |
| Reject | `button-destructive` "Rechazar" opens a `<dialog>` with a required reason: a textarea of at most 500 characters with a counter, matching the 5.3 note (FR-COM-3 requires a reason but sets no length). The reason is shown to the business verbatim in 7.1, so the hint says "La tienda verá este motivo. No incluya datos bancarios completos." Actions "Rechazar recarga" / "Cancelar" |
| After a decision | The dialog closes; the request leaves the Pendientes tab; the next pending request opens; the live region announces the outcome, naming what it did: "Recarga confirmada. Tienda Andrés tiene ahora $50.000 y sus publicaciones se reactivaron." / "…y sus publicaciones siguen pausadas." / "Recarga rechazada. Tienda Andrés verá el motivo." |
| Lost race | `TopUpNotPending`: the dialog closes, the detail re-fetches, and an `explainability-banner` (refusal tone) shows the §5 copy, for example "Sebastián ya confirmó esta recarga el 9 oct 2026, 11:15 a. m." |

## Page States

| State | When | Appearance | Actions |
|-------|------|------------|---------|
| Loading | Fetch | `skeleton` list + detail | — |
| Empty | No pending requests | "No hay recargas pendientes." | Ver confirmadas |
| Selected | A pending request | Detail + Decision | Confirmar recarga, Rechazar |
| Deciding | Dialog sent | The dialog's primary button reads "Confirmando…" / "Rechazando…" and both buttons are disabled | — |
| Decided | Confirmed or rejected tab | Read-only detail with the decision, the admin's name and time, and the reason if rejected | Ver movimientos de {tienda} |
| Lost race | Another admin decided first | Banner naming who and when | — |
| Error — validation | Reason empty | `field-error` "Escriba el motivo que verá la tienda." inside the dialog | — |
| Error — transport | Decision not confirmed | §10 "No sabemos si…" copy inside the dialog; "Actualizar" re-fetches the request, and its status answers the question. No automatic retry | Actualizar |
| Not available | Unknown id, or not an admin | Not-available page | — |

## Technical Notes

- The list polls every 30 s while visible and refetches on focus (EXPERIENCE Polling rule), so a second admin sees a decided request leave the queue.
- The decision is a conditional update `Pending → Confirmed | Rejected`. The credit and the replenished check run in the same transaction (FR-COM-3). The page never computes the new balance on the client; the preview and the result message come from the server.
- The confirm dialog is justified under EXPERIENCE's dialog rule: a credit is irreversible in V1, because refunds and reversals are out of scope.
- The `TopUpConfirmationPort` hides whether confirmation is manual (V1) or automated later. This page is the V1 manual adapter's UI.
