## Overview

**Page Purpose:** Make the trade state machine and its concurrency guarantees visible: drive any fixture offer through every transition as either party, fire two accepts at once on a last-unit listing (same listing and the sibling variant), advance the virtual clock past `expiresAt` to run the sweep, and get a pass or fail verdict checked against the NFR-TRD-1 invariants.

**Success Criteria:**
- The NFR-TRD-1 preset and its sibling variant each run ×100 and report PASA only when every iteration holds every invariant, including 0 deadlock aborts.
- Every command shows its Decision, its JSON and the resulting offer and listing state side by side.
- A failing iteration can be replayed from its seed.

**Entry Points:** The `/dev` index; "Ver en consola" from 4.3 (Inventory Console & Race Simulator) for a trade-vs-purchase run.

**Exit Points:** 8.2 of a fixture offer ("Abrir como {actor}"); the `/dev` index.

## Page Sections

### Section: Console Header

**OBJECT ID:** `trd-dev-header`

| Property | Value |
|----------|-------|
| Banner | "Consola de desarrollo · datos de prueba" |
| Actor switcher | Valentina (seller) · Julián (proposer) · a seed proposer for competing offers · Sebastián (admin, to show the FR-TRD-3 refusal and aggregate counts) · anónimo |
| Virtual clock | +1 h · +48 h · +7 d · fecha exacta. Crossing an open offer's `expiresAt` does not change it by itself; the sweep does (see Sweep) |
| Reset | "Restablecer fixture" returns the chosen preset's offers and listings to their starting state |

### Section: Presets (Plantillas)

**OBJECT ID:** `trd-dev-presets`

| Preset | Setup | Action | Invariants checked |
|--------|-------|--------|--------------------|
| **UJ-2 Valentina ↔ Julián** | Lote Psíquico open to trade; Gardevoir ex shared with the individual listing; one more open offer on each | Step through: offer (5 oct, 7:30 p. m.) → counter (6 oct, 8:15 a. m.) → accept (6 oct, 12:40 p. m.) → confirm ×2 (10 oct) | After accept: Gardevoir unit 0; both listings 0 available; 2 offers Unfulfillable with `ListingNoLongerAvailable`; 1 `TradeAccepted`; 1 handoff recorded by the listings fake; `completed` false → true only after the second confirmation |
| **NFR-TRD-1: dos aceptar en dos pestañas** | A last-unit listing with two Open offers (seller's turn) | Valentina accepts both concurrently from two sessions, ×100 | Exactly 1 Accepted with `reservationRef`; the other Unfulfillable; its request got `InsufficientQuantity` or `TradeOfferNotOpen`; quantity 0, never negative; 1 event; 1 handoff; 0 Open offers left on the listing |
| **NFR-TRD-1 hermanas: lote + individual** | An individual listing and a bundle sharing one last unit; one Open offer on each | Accept both concurrently, ×100 | Same invariants across both listings (`exhaustedListingIds` = both); **0 deadlock aborts** |
| **Intercambio vs compra (NFR-TRD-3)** | A shared last unit; one Open offer and one purchase attempt | Accept and `orders.create` concurrently, ×100 | Exactly one wins; never oversold; the losing purchase gets `InsufficientQuantity`; a losing accept leaves its offer Unfulfillable |
| **Vencimiento (barrido)** | Open offers with `expiresAt` in the past on the virtual clock, plus one Accepted trade | Run the sweep twice | Open → Expired exactly once (idempotent); the Accepted trade is untouched (FR-TRD-9); an accept after expiry gets `TradeOfferNotOpen` |

Each preset has "Ejecutar" and, where concurrency is involved, "Ejecutar ×100". Every run shows its seed, which can be pasted back to replay it.

### Section: State Machine

**OBJECT ID:** `trd-dev-machine`

| Property | Value |
|----------|-------|
| Component | `state-machine-viewer` |
| Nodes | Open · Accepted · Rejected · Withdrawn · Expired · Unfulfillable · Cancelled; "Completado" is drawn as a computed badge on Accepted (both confirmation timestamps set), not as a node |
| Current node | Highlighted with the "estado actual" label; `turn`, `version`, round count and both confirmation timestamps are listed under it |
| Transition list | Always rendered as text below the diagram: action, who may take it, guard (status, turn, version), effect on the reservation |

### Section: Command Panel

**OBJECT ID:** `trd-dev-command`

| Property | Value |
|----------|-------|
| Commands | offer · counter · accept · reject · withdraw · confirm · cancel · get (read) |

### Section: State and Result

**OBJECT ID:** `trd-dev-result`

| Property | Value |
|----------|-------|
| Listings | Availability per affected listing (including siblings) |
| Offers | Counts per status for the fixture, and each offer's status with its last round |
| Events | `TradeAccepted` count; handoff calls recorded by the listings fake, with their `tradeSummary` |
| Verdict | `race-simulator` result: "PASA {n} / FALLA {m}" and one line per invariant with ✓ or ✗ plus the observed value, e.g. "Iteración 12: 2 ofertas Accepted (se esperaba 1)". "Reproducir" replays a failing iteration step by step |
| Timing | p95 accept and other-action times of the run next to the NFR-TRD-2 targets (≤ 800 ms, ≤ 500 ms), as information only. The CI test is the gate |

## Technical Notes

- The console calls the real `trading` handlers through the §16 two-actor harness; the listings stub is replaced by the real `listings` module when the preset involves reservations, so the race exercises the same transaction path as production.
- Concurrency is real: ×100 presets issue the two accepts in parallel against the database.
- Deadlock aborts are counted from the database error class, not inferred from timings.
- The page is excluded from production builds by route configuration; the banner is a second line of defence.
