## Overview

**Page Purpose:** Let Andrés review the buyer's uploaded comprobante and confirm "payment received" (FR-S7, FR-S8, CAP-17, CAP-20, CAP-22).

**User Situation:** He opens an order from 4.1 to actually verify it — checking a comprobante image against his bank record is a deliberate task he does sitting at his desktop, not a one-thumb glance.

**Success Criteria:** He can clearly view the comprobante and record his own confirmation; he correctly understands he cannot close the order himself.

**Entry Points:**
- 4.1, tapping an order row.

**Exit Points:**
- Stays on page after confirming (status updates in place); back to 4.1 via back navigation.

| Property | Value |
|----------|-------|
| Purpose | Let Andrés inspect the payment-proof photo the buyer uploaded |
| Component | [`components.comprobante-viewer`](../../../DESIGN.md) — deliberately a read-only viewer, not an upload-dropzone, since Andrés only reviews, never uploads, this file |

#### Report Comprobante Issue Link

**OBJECT ID:** `order-detail-comprobante-report-issue-link`

| Property | Value |
|----------|-------|
| Component | Plain text link, `typography.meta` |
| Content | "Report an issue with this file" |
| Behavior | Appears only after 3 consecutive failed load attempts on the comprobante viewer (see Page States' Error row). Opens a minimal report flow (reason text + submit) that flags the order for manual follow-up — it does not resolve the corrupted file itself, only escalates past the retry loop. Never shown on a first or second failure, where a plain Retry is still the more likely fix |

## Page States

| State | When | Appearance | Actions |
|-------|------|------------|---------|
| Paid, unconfirmed by seller | Buyer paid and uploaded comprobante, Andrés hasn't confirmed yet | Comprobante viewer populated, Confirm button enabled | View comprobante, confirm receipt |
| Confirming | Confirm button tapped, request in flight | Confirm button disabled | None (guard against double-tap) |
| Seller-received-confirmed | Andrés confirmed | Status row updated, Confirm button replaced by the buyer-closes-only note | Wait for buyer to close |
| Closed | Buyer has also closed the order | Status row shows Closed, fully read-only | None — historical record |
| Error | Comprobante fails to load | Placeholder with "Couldn't load the payment proof — try again" and a retry action scoped to the viewer only; after the 3rd consecutive failure, "Report an issue with this file" also appears | Retry loading the image; report an issue (after 3 failures) |

## Technical Notes

- This page is the canonical example of AD-2's consequence for the business side: Andrés's confirmation is one of three independent confirmations that make up an Order's lifecycle, and this page only ever writes his one (`sellerReceivedConfirmedAt`) — it never writes the Closed state, which requires the buyer's own action on their own device.
- The comprobante-viewer's read access to the buyer's uploaded file is governed by the shared cross-track comprobante-storage ACL decision made in the Buyer/Collector track's ARCHITECTURE.md (AD-14) — this page assumes that access is already granted, it does not itself decide the ACL.
- An order that reaches Seller-received-confirmed and then sits there indefinitely because the buyer never closes it is an accepted terminal-ish state, not a bug this page works around — consistent with this track's existing no-SLA/no-auto-escalation stance elsewhere (CAP-15's manual verification review). This page shows no staleness warning, no reminder nudge, and no timeout on the buyer-closes-only note; only the buyer's own action ever advances the order further.
- A corrupted/unreadable comprobante upload is distinguished from a transient network failure only by retry count (3 consecutive failures), not by inspecting the file itself — the client has no way to tell "bad network" from "bad file," so the escalation path is offered defensively after repeated failures rather than diagnosed precisely.
