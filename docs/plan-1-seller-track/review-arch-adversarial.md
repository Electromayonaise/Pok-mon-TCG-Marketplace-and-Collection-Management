# Adversarial Review — Seller/Business Track `ARCHITECTURE.md`

**Reviewed:** `docs/plan-1-seller-track/ARCHITECTURE.md`
**Method:** `bmad-review-adversarial-general`
**Cross-referenced against:** `docs/plan-1-buyer-track/ARCHITECTURE.md`, `docs/plan-1-seller-track/prd.md`

---

- **AD-18's "same transaction" framing does not actually prevent the concurrent-approval race it claims to close.** The Rule states "both checks run inside the same transaction as the write they're guarding, so no interleaving of the two actions can produce a moment where both flags read true" — but a transaction wrapping a check-then-write only serializes against the *other* transaction if the check itself is expressed as part of a locking write against the same row (e.g. an `UPDATE ... WHERE <guard>` whose affected-row-count is checked), not a plain `SELECT` followed by an `UPDATE`. As written, two concurrent transactions — one completing the individual-seller profile, one approving the business application, both against the same user — could each read the other's flag as still unset before either commits, and both proceed. AD-19, two paragraphs later, is far more careful about exactly this class of race and names its closing mechanism explicitly (a single atomic conditional `UPDATE`); AD-18 makes an equivalent "interleaving is impossible" claim with none of that rigor.

- **The Capability → Architecture Map's first row misattributes AD-19 as an inherited SPINE decision.** The row "CAP-4, CAP-16, CAP-19 (individual-seller listing, profile step) | `listings`, `identity` | AD-1, AD-19 (SPINE) — inherited" labels AD-19 as part of the whole-system spine. Every other section of this same document — the frontmatter `scope`, the Cross-Track Note, AD-19's own header, and even a later row in this same table ("CAP-21 ... AD-3 (SPINE, inherited), **AD-19 (new)**") — states unambiguously that AD-19 is this track's own new decision. This is an internal factual contradiction, not a stylistic issue.

- **AD-18's binary model has no representation for a `Pending` business application, which FR-S9 explicitly requires.** FR-S9 lets a business "create a listing while its application is still `Pending`" (`sellerType=business`, not yet purchasable). But AD-18's exclusivity check fires only against a non-null `businessId`, and the Rule states `businessId` is set at *Approval*, not at submission. Nothing in this file explains what field distinguishes "has a Pending business application" from "plain individual seller" for FR-S9's own purposes — the exclusivity model this file designs doesn't actually cover the state FR-S9 depends on existing.

- **Following directly from the above: AD-18 does not close the exclusivity gap during the `Pending` window.** Because the check only trips on a non-null `businessId`, a user whose business application is sitting `Pending` could still complete the individual-seller profile step with no rejection at all — nothing stops it. This directly undercuts the Cross-Track Note's claim that OQ4 (reapplication with no cooldown, meaning a user can cycle back into `Pending`) "carries no cross-module divergence risk" and was correctly left off the AD list. It interacts with AD-18 in exactly the way that "would two independently-built units diverge" test exists to catch, and nothing here notices it.

- **AD-19 never states the mechanism, or even the existence of a dependency, that prevents the *same* Order's confirm-payment-received call from double-deducting on retry.** AD-19's own text only analyzes two *different* Orders confirming concurrently. A client retry (e.g. after a network timeout) hitting the same Order's confirm-payment-received endpoint twice would call AD-19's atomic `UPDATE` twice unless the adopted `OrderAlreadyConfirmedByRole` check (from the Buyer-track file, owned by `orders`) runs first, in the same transaction, and gates the commission `UPDATE` from ever firing on the second call. That sequencing dependency across two modules (`orders` gating `commission`) is never stated anywhere in this file.

- **AD-19 conflates two separable design choices — atomicity and negative-balance tolerance — as if the second follows necessarily from the first.** An atomic conditional `UPDATE` could just as easily include a floor guard (`WHERE balance >= :amount`) without reintroducing either a read-modify-write race or a pessimistic lock. That third alternative — atomic *and* floor-guarded — is never named or rejected in AD-19's Rejected Alternatives list, which considers only a pessimistic row lock and no atomicity guard at all. The actual chosen trade-off (no floor guard, transient negative balances allowed) is a legitimate answer to PRD OQ6, but it's under-justified as written, since the alternative that would have avoided it entirely was never on the table.

- **The Structural Seed diagram's `Verify -->|AD-19 atomic decrement| commission_m` edge misattributes which UI surface triggers commission deduction.** Andrés confirming a sale on the Orders/4.2 surface is what triggers the decrement, per AD-19's own Binds line and Rule text ("in the same transaction as setting `sellerReceivedConfirmedAt`"). The Verify subgraph (3.1-3.3, including the balance page) only reads and tops up the balance. The diagram already has a second, correctly-labeled edge for the real trigger (`Orders -->|FR-S8 confirm, triggers AD-19| commission_m`) — the Verify edge is redundant at best and actively misleading at worst.

- **The file's own frontmatter sets `status: final` while its `reviewed:` field and closing note both state the Reviewer Gate hasn't run yet.** A document cannot simultaneously be final and pending the review that would qualify it as final. This isn't a stylistic quibble — a grader or downstream tool skimming only the frontmatter status field would take `final` at face value and never reach the caveat buried in prose below it.

- **The frontmatter `binds` array is narrower than what the ADs it summarizes actually claim to bind.** It lists only `FR-S8` among this track's own FR-S numbers, but AD-18's own Binds line names FR-S1 and FR-S5, and AD-19's own Binds line names FR-S6 in addition to FR-S8. The top-level summary field disagrees with the body it's supposed to be summarizing.

- **The Buyer-track `ARCHITECTURE.md`'s `companions` field is now stale and nothing here flags it.** That file still describes this one as "prospective — not yet written as of this file's finalization." Producing this file without a note back to the Buyer-track file (or at least flagging the dangling cross-reference) leaves a reader following the trail backwards from that file to hit an outdated pointer.

- **The standard applied to "does this concurrency question deserve a new AD" is inconsistent between AD-19 and the OQ2 disposition.** The Cross-Track Note dismisses OQ2 (concurrent trade-offer acceptance against the same `InventoryUnit`) as carrying "no cross-module divergence risk," resting entirely on a one-line citation to inherited AD-6. But AD-19 treats a structurally analogous concern — two near-simultaneous writes touching a shared numeric resource — as warranting a dedicated new AD with an explicitly named atomic mechanism. If the commission-balance race was worth a new AD, the parallel inventory-reservation race arguably needed at least a sentence restating that AD-6's existing mechanism is itself atomic, rather than a bare citation.

- **Minor: the frontmatter `scope` field undersells what the file actually does.** It describes the job as resolving "this track's own open decision (AD-18)" and "one carried-forward PRD open question" (AD-19), but the Cross-Track Note goes further and adjudicates the disposition of all six PRD Open Questions (OQ1-OQ6). Not a defect, but a documentation-completeness mismatch between the summary and the body.
